# 高清渲染、透明边缘与性能

[返回目录](../README.md)

## 接入后变糊，先查尺寸链

按顺序检查原画 → 图集 → MOC 中 UV → 渲染缓冲 → 合成缓冲 → 页面显示尺寸。

源图清楚但网页糊，常见原因是 Canvas 后备尺寸不足，尤其 CSS transform 放大后仍按未变换的尺寸分配。布局宽度和实际屏幕显示宽度不是总相同。

所有绘制通道、遮罩与合成目标应对齐同一尺寸契约。只把最终 Canvas 放大，会把前面已经丢失的细节一起放大。

## 项目采用过的高清方案

在用户确认的同尺寸对照中，采用了最高约 3 倍采样、最长边限制 2048、支持时使用高精度片元计算，再用预乘 Alpha 的可分离 Lanczos-2 缩回显示像素。局部范围限制用于减轻锐化振铃。

这些是项目参数，不是设备无关的最佳配置。它改善小尺寸睫毛、发丝和衣服边缘的采样表现，没有增加原画不存在的细节。

## 对照必须公平

- 相同 CSS 尺寸、相机、背景、动作时间、鼠标输入。
- 全身看实际使用效果，脸部近景用独立相机。
- 不把左侧小图与右侧大图比较，也不把近景简单解释为“高清”。
- 如果同时渲染多个模型，记录它对帧率的影响。
- 动作时间要共享；否则一张睁眼一张半闭眼会误导判断。

## Alpha 错误会像美术问题

检查图像是否已经预乘、上传纹理时如何处理、着色器输出约定以及混合方式。重复预乘、该预乘时未预乘、或在错误阶段重新解释颜色，都会影响边缘。

官方[剪贴蒙版文档](https://docs.live2d.com/en/cubism-editor-manual/clipping-mask/)还说明了蒙版边缘半透明叠加可能露出底层颜色的机制。白边不一定都是抠图残留，应分别检查素材、蒙版和合成。

## 单模型并不自动轻量

本项目阶段性双外观模型有 27 张 2048×2048 图集。仅按未压缩 RGBA8 一级纹理估算约 432 MiB，还没计入额外缓冲、mipmap 或驱动开销；这是估算，不是 GPU 实测。

一个模型、多次面部合成、超采样和多个预览视图都可能增加开销。应同时记录：

- 实际 Canvas 与图集大小；
- 帧耗时、帧率和动作墙钟时长；
- 绘制次数和纹理数；
- 页面隐藏时是否暂停；
- 销毁时是否释放 WebGL 与监听器资源。

历史高负担预览曾出现约 7–13 FPS，不能用“高清通过”推导“性能也通过”。先在目标设备、单角色实际页面测试，再决定是否降低采样或优化图集。

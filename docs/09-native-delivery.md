# 原生工程、导出与版本交付

[返回目录](../README.md)

## 哪个文件负责什么

| 文件或组件 | 职责 |
|---|---|
| PSD / 分层原画 | 可编辑素材与遮挡补全 |
| CMO3 | Cubism 编辑工程 |
| MOC3 | 运行时模型数据 |
| model3.json | 模型相关资源的入口与引用 |
| 纹理图集 | 网格使用的像素 |
| motion3.json | 参数随时间的变化 |
| exp3.json | 表情参数设置 |
| physics3.json | 使用官方物理流程时的配置 |
| 宿主控制器 | 鼠标、动作选择、外观状态、额外合成和转场 |

运行文件关系参考官方[Web 模型说明](https://docs.live2d.com/en/cubism-sdk-manual/model-web/)和 [model3.json 规格](https://github.com/Live2D/CubismSpecs/blob/master/FileFormats/model3.json.md)。

“原生模型”不保证任意宿主都复现网页附加特效。交付时要明确哪些来自模型，哪些依赖控制器。本项目发尾曾使用自定义弹簧驱动而非 physics3.json；烘焙动作可以包含发尾参数，实时跟随仍需要驱动。

## 提前算编辑器预算

统一动作和两套外观之后，项目超过了当时 FREE 的预算，使用官方 PRO 试用完成编辑和导出。不要等全模型整合完才发现无法保存。

2026-10-20 核对时，官方[FREE / PRO 对比](https://www.live2d.com/en/cubism/comparison/)列出 FREE 的相关限制：100 个 ArtMesh、30 个参数、单张最大 2048 纹理。完整功能与适用条件以官方页面和目标版本为准；本轮没有重新核验许可上限。本笔记不提供绕过限制的方法。

网格数和参数数也不是全部资源预算。多个参数同时作用于对象时，要检查关键形组合增长、图集占用、载入和保存成本。官方 [X/Y 制作教程](https://docs.live2d.com/en/cubism-editor-tutorials/xy/)用参数组合说明这一问题，并介绍用变形器拆分管理。先分析参数依赖和对象职责，再决定分层或减少组合，不应仅为省资源降低已确认画质。

## 卡住先看证据，再决定重启

编辑器长时间停在载入窗口，不能仅凭现象断定内存耗尽。检查对应日志、资源使用、文件解析错误和加载阶段；脚本生成候选在送入 Editor 前，应校验整数/浮点等字段类型、引用、索引与对象数量。日志若明确是字段解析失败，应先修数据，不反复重启碰运气。

保存与导出都要有成功证据；窗口消失或文件出现不是充分条件。重启前保护未保存工程，保留错误日志和可回退候选。这里是诊断顺序建议，不将每次卡顿归为同一个根因。

## 改几何与改像素的交付路径不同

**几何、关键形、参数或绘制顺序改变：**

源工程备份 → 修改 → 官方 Editor 打开与保存 → 导出 MOC3 → 目标 Core 检查 → 宿主视觉回归。

**只改既有图集内的像素：**

若图集索引、尺寸、UV、槽位与透明度契约保持一致，可替换对应纹理，不必为像素变化重编译几何。源工程中的素材/内嵌图集也要同步，否则下次导出可能覆盖修复。

同理，不能为“保留高清”在新导出后直接拷回旧图集。必须逐项验证新几何与旧纹理的对应契约，明确哪些槽位应字节一致、哪些允许重编码但像素一致、哪些确实更新。该核对结果也属于交付清单。

具体操作取决于工程管理方式；不要假设所有 CMO3 内部结构都能用同一个脚本安全修改。本项目的归档辅助是特定版本工具，不能当官方稳定格式 API。

## 不要用临时运行补丁冒充原生修复

马尾遮挡曾由网页排序辅助验证，最终写回原生绘制顺序并重新导出，之后删除临时排序。若只保留网页补丁，换查看器就可能复发。

直接改 MOC 二进制不作为本仓库推荐工作流。需要原生变化时优先保留可编辑工程并走官方导出。

## 交付清单

交付包应包含资源入口、动作和外观覆盖说明、宿主依赖、版本、图集数量与尺寸、校验清单、回退基线及验证范围。明确鼠标输入坐标、单位和参数范围，避免重复物理和参数覆盖。

把源工程、MOC、纹理、动作与控制器版本一起固定。名称里出现 `final` 或 `delivery` 不足以识别最后采用版本；任何后续接缝修补都要注明哪些检查重跑了，哪些仍属于前一候选。原生已导出、用户已确认、本地已同步和线上已发布是四种不同状态。

大模型与原画通常需要独立资产存储或 Git LFS；这份知识库只保存文档和轻量示例，避免把不可再分发的 SDK 或角色素材混入公共仓库。

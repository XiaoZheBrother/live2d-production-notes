# 单一原生主模型与全动作换装

[返回目录](../README.md)

## “一个模型”解决了什么

本项目把九个动作放进一个原生主模型，由统一控制器驱动。九个动作是待机、翻书、挥手、思考、鼓励、倾听、失落、害羞、崇拜。

但一个 MOC3 内仍可能保留动作专用脸层、袖子或手部。它不自动等于全部动作共享同一套拓扑，也不意味着模型更省显存。应分别说明文件数量、重复部件、绘制次数和宿主依赖。

## 外观状态必须独立于动作

```text
外观选择
├─ hairstyle
├─ outfit
└─ accessories[]

动作状态：idle / bookTurn / wave / ...
主题状态：resolved light / dark
```

动作读取外观状态，不能在进入或返回时重置它。主题跟随系统时，使用页面已经解析出的有效主题，避免角色与页面各算一套。

## 最容易遗漏的部件

只换待机衣身不够。抬手袖子、翻页袖口、手掌图里夹带的旧布料、崇拜的独立头部和衣服，都可能留下旧造型。

建立覆盖表，按“外观 × 动作 × 必需部件”检查：

| 类别 | 普通姿态 | 特殊姿态 |
|---|---|---|
| 发型 | 前后发、侧发、马尾、发饰 | 崇拜等专用脸层里混入的旧头发 |
| 服装 | 衣身、裙、腿、鞋 | 各类抬手袖、翻书袖、手部混合图 |
| 饰品 | 眼镜、胸针等 | 手遮脸、闭眼、倾斜头部时的遮挡 |

每项必须明确是复用原部件、替换纹理、切换原生网格，还是由宿主附着。只有待机截图不足以证明换装完成。

## 原子提交与加载竞态

一次选择应先校验完整覆盖、预加载，再整套提交。A 外观加载慢、B 外观后选却先完成时，不能让 A 最后覆盖 B。加载失败保留完整旧外观。

本仓库[教学示例](../examples/runtime-patterns.mjs)使用请求序号验证这种行为。完整产品还应考虑取消加载、GPU 资源释放、缓存和失效配置迁移。

## 配色、换纹理、换轮廓是三种工作量

| 变化 | 可能复用 | 还需做什么 |
|---|---|---|
| 配色 | 现有轮廓与拓扑 | 保护肤色、眼睛、书与图案 |
| 同轮廓换布料 | 既有 UV 和网格 | 配准、边界与全动作检查 |
| 高马尾、新衣型 | 部分基础参数 | 新原画、遮挡补全、网格、关键形、层级和动作覆盖 |

日常高马尾候选曾因不够自然而暂缓。后续暗夜高马尾是另外一套设计与验证结果，不能把早期“可选择”误记为最终通过。

## 层级也属于模型契约

马尾需要在肩后，应修对应原生绘制顺序和相关关键形。网页里临时强制排序可帮助诊断，但换宿主后不会自动存在。

原生层级案例见[马尾修复](../cases/03-hair-order.md)，导出注意事项见[第 9 章](09-native-delivery.md)。
